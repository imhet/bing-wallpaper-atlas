# 壁纸第二天就消失，所以我给 Bing 每日壁纸做了个搜索引擎

> 项目地址：https://github.com/imhet/bing-wallpaper-atlas
> 在线访问：https://imhet.github.io/bing-wallpaper-atlas/

## 起因：留不住的每日一图

Bing 每日壁纸大概是互联网上最良心、也最任性的免费图库。

良心在于：每天零点，首页换上一张精选摄影——大多是风光大片，配着拍摄地点、摄影师和一小段背后故事，免登录、免付费、无水印。任性在于：第二天零点，这张图就从首页下线，官方不提供任何归档入口。哪天忘了截图，它就只剩搜索引擎缓存里的残影。官方接口 `HPImageArchive.aspx` 也只保留最近 15 天。

比图更可惜的是元数据。「冰岛塞里雅兰瀑布，摄影师某某」——这句描述本身就是信息：拍摄地在哪、谁拍的、背后有什么故事、原图有哪些分辨率。图丢了可以再找类似的，这些结构化的信息丢了就真没了。

于是需求变得很朴素：

1. 把历年的壁纸连同元数据全部存下来；
2. 能搜——按地点、时间、市场、摄影师，最好还能按画面内容搜；
3. 不想为它维护一台服务器。

这个项目就是这三个需求的答案：**3475 条记录、6 个市场、2272 张唯一图，一套流水线加一个静态站，零服务器，每天早上 6 点自动更新。**

## 怎么做：一套流水线 + 一个静态站

架构一句话说清：Python 抓取 → 分片 JSON → Vue 3 静态站 → GitHub Actions 全自动。

```
niumoo 仓库 images.json（历史回填）    Bing 官方 API（近 8 天增量）
            └──────────────┬──────────────┘
                     build_record()：拼 15 字段记录
                     copyright 解析 © 提取摄影师/图库
                     regions.py 国家归一 + geo_enrich 地名标签
                           ↓
              data/{market}/{year}.json 分片 + aggregations.json
                           ↓
        Vue 3 + MiniSearch 浏览器内搜索，GitHub Pages 托管
                           ↓
        GitHub Actions 每天 UTC 22:00 抓取→打标→提交→部署
```

几个关键决策：

**双源数据。** 历史数据来自 niumoo/bing-wallpaper 仓库的多年归档（en-us 从 2021-02、zh-cn 从 2023-02），每日增量走官方 API。增量源还做了「市场预检」——Bing 会按请求出口的网络位置覆盖 `mkt` 参数，有些市场在美国出口拿到的 feed 是被路由污染的，预检不过就剔除，宁缺毋滥。

**图片永不落地。** 仓库里只有元数据 JSON，图片始终直链 Bing CDN。这一半是版权上的克制（图片版权归 Microsoft 和原作者，站点只做元数据索引），一半是工程上的省心——仓库至今只有 2.6MB。后文的内容打标也遵守这条纪律：缩略图拉进内存推理，用完即弃。

**分片 JSON 当 API。** 按「市场/年份」切成 14 个分片，前端惰性加载，首屏只拉目标年份的分片（约 80KB）立刻渲染，其余分片后台静默补齐。没有后端，静态托管就是全部。

**浏览器内搜索。** MiniSearch 在浏览器里建倒排索引，3475 条记录全量建索引毫秒级完成，搜索零网络请求。

## 搜索：三层进化

这个项目里做得最久、踩坑最多、也最有意思的部分，是搜索。

### 第一层：中文搜索的字面陷阱

中文没有空格分词，通用全文检索直接用会闹笑话。我的 tokenizer 把查询切成「单字 + 相邻二元组」：`中国雪山` → `中 / 中国 / 国 / 国雪 / 雪 / 雪山 / 山`。

单字负责字面召回——保证含「雪」含「山」的图不至于漏掉；二元组负责精确——AND 匹配要求「中国」作为连续词出现，否则搜「中国」会命中所有「国家公园……框景**中**」这类字符共现。AND 全落空时回退词组级 OR，保证有结果。

这个设计后来还修过一个隐蔽 bug：二元组是从分词结果按数组相邻拼的，`布莱耶斯湖，南蒂罗尔` 里「湖」和「南」隔着全角标点被拼成了假词「湖南」——修复方式是回到原文位置判断真正的相邻关系。排查时发现，全库 56% 的记录都带着这类假词。

### 第二层：跨语言桥接，以及一场词典误挂排查

新的痛点：en-us 市场的图描述全是英文，搜「优胜美地」找不到 Yosemite 的图——尽管两边说的是同一批风景。

解法是一本多语言地名词典：647 组别名，每组是同一个地方的不同写法（优胜美地 = yosemite = ヨセミテ = 優勝美地）。入库时文本命中组内任一写法，就把整组别名写进这条记录的 tags。搜索端零改动，跨语言召回自动成立。

再进一步是行政区划层级：347 条「子地名 → 父行政区」映射，命中「张家界」自动挂上「湖南」的 tags——搜「湖南」能召回张家界，哪怕文字里从没出现过「湖南」两个字。

然后是本项目最著名的一次翻车：**一张瑞士劳特布伦嫩瀑布的照片，被打上了「广州」的标签。**

排查发现根因既好笑又合理：伯尔尼州的官方写法是 *Canton of Bern*，而 *Canton* 恰好是「广州」的旧英文译名（Canton、Canton Fair 的那个 Canton）。词典里「广州」组挂着 `canton` 这个别名，词边界匹配严丝合缝地命中了。

canton 没错，错的是语境。顺着这条线索做了一次全量排查——匹配语义 × 全库记录 × 全部别名，再交叉验证「命中地名组 vs 文本里归一出的国家」是否矛盾——挖出 **166 条误挂**，归为三类：

1. **裸英文常见词别名**：`island → 冰岛`（62 条！）、`indian`、`american`、`french`……词边界挡得住子串，挡不住常用词本身；
2. **CJK 子串**：中文没有词边界，「佛罗里达**州**」含「达州」、「都柏**林**」含「柏林」、「罗马尼亚」含「罗马」、「纽芬**兰**」含「芬兰」；
3. **专名撞名**：捷克的 *Bohemian Switzerland*（波希米亚瑞士）不是瑞士、斯里兰卡的「爱丁堡茶园」不是爱丁堡、阿拉斯加的「荷兰港」不是荷兰。

修法是给词典加「否定上下文」：每个易撞名的地名组配一份否定词表（「柏林」组见到「都柏林」不命中，「瑞士」组见到 `bohemian switzerland` 不命中），加上删掉全部裸常见词别名。166 条误挂清零，且全部进了测试锁死防回归。

### 第三层：画面内容搜索——文字到不了的地方

文字层搜索有个天花板：壁纸的文字描述极少写画面内容。统计了一下，中文语料的描述里含「雪」字的只有 26 条，搜「雪山」零召回。**文字里没有的词，文字搜索永远找不到。**

解法只能是让机器「看图」打标签。

**第一版：CLIP 零样本分类。** open_clip 的 ViT-B-32，配一份百余个概念的词表（雪山/佛像/小熊猫/珊瑚礁/烟花……），每张图的缩略图拉进内存过一遍模型，取相似度 top 概念写进 `content_tags` 字段。搜「雪山」从 0 变成 282 条，目标达成。

但质量翻车了：熊猫图的画面标签里有猴子、山羊、长城、猫头鹰；乐山大佛的图里居然没有「佛像」。定位到两个根因——词表缺正确概念时，CLIP 的 top 分数全挤在 0.2 附近没有区分度，错的词表条目就顶上来了；B-32 本身区分度弱，阈值又放得太松。升级到 ViT-B-16、收紧相对阈值、补全词表，好了不少，但天花板明显：**闭集分类的世界里，词表外的概念永远打不出来。**

**第二版：多模态大模型。** 换成 VLM（glm-5.3-flash）做开放理解，prompt 只约定四件事：输出画面主要实体的中文标签 JSON 数组；动物到物种、建筑到类型；知名地标输出通用中文名；不要情绪氛围词，最多 6 个。

效果是代差级的：「乐山大佛」「云冈石窟」「红墙」「幼鲸」「绯红金刚鹦鹉」——专名级标签，全部不在任何词表里，是模型自己看出来的。当前真实数据（3475 条记录）：

| 搜索词 | 命中 | 说明 |
|---|---|---|
| 雪山 | 189 | 文字层时代为 0 |
| 乐山大佛 / 云冈石窟 / 红墙 | 2 / 2 / 2 | 全靠 VLM 专名识别，词表里没有 |
| 优胜美地 / yosemite | 18 / 17 | 词典桥接 + VLM 中文标签双通道 |
| 烟花 / 极光 | 14 / 10 | 画面内容 |

VLM 也不是白来的，两个坑记在此处供后人乘凉：

- **`max_tokens=400` 会把 JSON 截断在半截**——VLM 的 thinking 块也计入输出配额，首轮 70 张图的回复全断在 `["教堂", "乔鲁拉大金字塔` 这种地方，静默降级回了 CLIP。改到 1024 后零降级。
- **编码套餐限流很紧**：10 并发全 429。3 并发加指数退避（2/5/10 秒）稳稳跑完——全量 2200 多张唯一图约 1.5 小时，约 90 万 token，按套餐价格折合几块钱。

最终架构是**双引擎**：VLM 优先，任何失败（未配凭证、限流退避耗尽、回复不可解析）自动降级本地 CLIP，每日增量的打标步骤 `continue-on-error`，模型挂了不阻塞部署，次日自动补打。

## 踩坑集锦：真正的成本都在这里

搜索之外，还有几个花时间远超预期的坑，记录下来：

**部署竞争。** 一次 push 被拒后误触发了强制部署，旧代码的定时任务用旧的词典数据 commit + push，把我刚修好的 166 条误挂数据**整个回滚**了。此后流程固化：push 之后必须核对部署 run 的 headSha 与远端一致，再 curl 线上分片核对内容（CDN 缓存用随机 query 绕过）。

**rebase 的 ours/theirs 与 merge 相反。** rebase 时 `ours` 指基底（远端），`theirs` 指正在重放的我方提交。取错一次边，把定时任务刚抓的新记录丢掉了，好在事后能从远端 commit 里按记录 id 捡回来。数据分片冲突后的标准动作是：对比两边记录数，缺谁的补谁的。

**测试与数据互锁。** 修词典 bug 时发现旧单测断言 `tags == []` 把 bug 固化成了预期行为。此后所有真实数据上的断言都用「≥ 基线」的写法——数据增长不断言上限，但防误报的「不得混入」用例（搜「广州」不得出瑞士图）一条条锁死。

## 成本与规模

- 服务器：0 元，GitHub Pages 静态托管；
- 数据：3475 条记录 / 2272 张唯一图 / 2.6MB JSON，仓库轻到可以直接 clone；
- VLM 全量打标：约 90 万 token，几块钱等值额度；每日增量每天只有 6-8 张图，成本忽略不计；
- 人力：每天早上 6 点 Actions 自动抓取、打标、部署，只有红灯时才需要人看一眼。

## 写在最后

回头看，这个项目最初始的动机其实是「不想让每天那张图就这么没了」，做出来却发现真正有意思的是搜索这三层：中文分词的字面陷阱是语言学问题，跨语言词典是数据工程问题，画面打标是「文字到不了的地方」——每一层都在补上一层的盲区。

图片仍不落地，图仍归 Bing 和摄影师们。这里只是留了一份索引，和那些差点消失的故事。
